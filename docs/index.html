让 NFrp 与官方 frp看得见、管得住

FrpPanel 是面向 NFrp（Rust-Frp） 与官方 frp（frps / frpc）的统一 Web 管理面板。 后端 Rust（Axum + SQLite），前端 Vue 3 + TypeScript。默认本机二进制模式，也可以选择 SSH 远程部署， 或只把一台已经在跑的实例通过 Admin API 纳管起来。面板不内嵌 Go 运行时，也不做黑盒中间层——每个动作都能在日志里找到对应命令。

核心设计

一套 DTO，两种 frp

driver trait 收敛差异，前端只认一份统一 DTO。NFrp 与官方 frp 的字段、端点差异全部在后端适配层吸收。

能力探测，不做假成功

不支持的能力在界面上灰化并说明原因，而不是假装成功。能力位是前端唯一的驱动差异来源。

列表先本地，后探测

打开面板先读本地记录秒开，再在后台逐个探测连接状态。探测失败只降低置信度并写入说明，不阻塞列表。

SSH 一键部署

预检 → SFTP 上传 → 校验 → 备份 → 原子替换 → systemd / nohup → 就绪轮询，失败自动回滚二进制与配置。

SSE 实时步骤

部署过程通过 SSE 实时推送步骤状态与日志，前端步骤条同步展示进度、失败原因与修复建议。

审计与 RBAC

admin 可写、viewer 只读，写接口在提取器层拒绝。凭据 AES-256-GCM 加密，日志与审计统一脱敏。

两种 frp 的差异

这是面板必须存在的原因：NFrp 与官方 frp 的管理面并不相同。下表来自实测（NFrp 0.7.4 / 官方 frp 0.71.1）。

能力NFrp 0.7.4官方 frp 0.71.1
服务端状态/api/status、/api/v2/status只有 /api/v2/clients、/api/v2/proxies
健康检查/api/healthz无（404）
客户端读配置无/api/config（返回 TOML 原文）
代理动态增删服务端推送 + 客户端 /api/proxies/add|remove不可用（PUT /api/config 返回 200 但不生效）
热重载轮询配置文件 mtime，无 HTTP 端点服务端无热重载；frpc 需 --enableReload

未知配置字段宽容零容忍（unknown field 直接退出）

安装与运行

面板由 Rust 后端与 Vue 3 前端组成。先用开发模式跑通，再用单进程模式部署。

前置依赖

依赖版本说明
Rust≥ 1.80后端
Node.js≥ 20前端，使用 npm
SQLite内嵌由 sqlx 自带，无需单独安装
OpenSSH 客户端任意仅 SSH 部署需要（sftp）；Windows 10+ 自带
nfrp-common源码通过 path 依赖本地 NFrp 仓库

1. 关联 nfrp-common

Cargo.toml 以 path 方式复用 NFrp 的配置解析与校验。这是「与 NFrp 同源」的具体体现，不是中间层。

nfrp-common = { path = "E:/项目/RustFrp/nfrp/common" }

把路径改成你本机的 NFrp 源码位置即可。

2. 启动后端

cargo run -p frp-panel -- --bind 127.0.0.1:8787

首次启动会在 data/ 下生成：

  • panel.db — 面板数据库（实例、凭据密文、审计、备份、任务）
  • master.key — 加密凭据的主密钥，权限收紧到 0600
  • jwt.key — 签发 token 的密钥，权限收紧到 0600
  • admin.initial — 管理员 admin 的随机初始口令，同时打印到控制台一次

也可以用 FRP_PANEL_ADMIN_PASSWORD 环境变量指定初始口令（仅首次创建时生效）。

两个密钥文件不能丢

master.key 丢失后已存凭据无法解密，需重新录入；jwt.key 丢失只会让现有 token 失效。两者都不要进版本库。

3. 启动前端（开发模式）

cd frontend
npm install
npm run dev      # http://127.0.0.1:5173，/api 代理到 8787

4. 生产模式（单进程）

cd frontend && npm ci && npm run build
cd .. && FRP_PANEL_STATIC_DIR=frontend/dist cargo run --release -p frp-panel
# 访问 http://127.0.0.1:8787

后端会把 static_dir 作为静态目录挂载，未命中的路径回退到 index.html，因此前端 SPA 路由可以正常工作。

5. 开发启动脚本

不想开两个终端时，可以直接用 dev.bat：

dev.bat            :: 后端 + 前端，自动选空闲端口
dev.bat status
dev.bat stop

忘记管理员密码

使用与后端相同的 Argon2 哈希重置，新密码从 stdin 读取，不会出现在进程列表里：

echo 你的新密码 | cargo run -p frp-panel -- --reset-admin-password --admin-username admin

成功后旧的 data/admin.initial 会被删除。此入口只适合本机管理员使用，不要包装成对公网开放的重置接口。

面板默认只监听回环地址

要暴露到公网请用 Nginx / Caddy 反向代理 + HTTPS，并保持 bind = 127.0.0.1:8787。详见安全说明。

快速开始

从零到在面板里看见一个实例，大约五分钟。

0. 准备

  • Rust ≥ 1.80、Node.js ≥ 20
  • 一份本地 NFrp 源码（提供 nfrp-common path 依赖）
  • 要管理的 frp 二进制（本机模式）或一台可 SSH 登录的 Linux 主机（远程模式）

1. 起后端与前端

# 终端 A
cargo run -p frp-panel -- --bind 127.0.0.1:8787

# 终端 B
cd frontend
npm install
npm run dev

也可以用 dev.bat 一条命令拉起两端，脚本会自动选择空闲端口。

2. 登录

开发模式访问 http://127.0.0.1:5173；单进程模式访问 http://127.0.0.1:8787。初始管理员名为 admin，口令在首次启动时写入 data/admin.initial。

3. 新建实例

在实例页新建实例，按你的场景选择驱动：

  • 本机实例 — binary，填二进制、配置文件、日志与工作目录，面板直接接管进程
  • 远程实例 — ssh_binary，填 SSH 主机、端口、用户、凭据与 sudo 方式，由面板完成部署
  • 已有实例 — admin_api，只填 Admin API 的 base_url、用户与密码凭据，不接管进程与配置

保存后后端会执行一次能力探测，并把版本、能力位与证据落库。实例详情页的「能力」页签可以直接看到结果。

4. 启停与观察

  • 启动 / 停止 / 重启：有明确的成功与失败反馈，不返回假成功
  • 状态：PID、运行时长、二进制版本、Admin API 是否可达
  • 配置：读取、校验、保存、备份与恢复；保存后可选择自动重启
  • 日志：按文件 / 远程 / journal 统一查看，支持 SSE 跟随
  • 监控：连接数、流量字节按时间范围查询；官方 frps 只有连接数级别

5. 确认后端在跑

curl http://127.0.0.1:8787/api/health

/api/health 免鉴权；其余接口需要 Authorization: Bearer <access_token>。

首次登录后立刻改密码

修改后删除 data/admin.initial，不要把这个文件留在磁盘上。

  • 要接接口或写脚本，看HTTP API

实例管理

一个面板管理多个 frps / frpc 实例，按实例隔离配置、日志、监控与凭据。

一台面板，多个实例

每个实例都有自己的驱动、实现类型（NFrp / 官方 frp）、连接方式、二进制与配置路径。实例之间不共享配置文件、日志目录、监控采样与凭据引用。面板数据库只保存引用（credential_id、password_secret_id），密文单独存放在 secrets 表中。

列表先本地，再探测

打开面板时，实例列表先读取本地记录立即渲染，不等网络探测；随后在后台逐个探测连接状态。这样即使某台机器离线、Admin API 不可达，列表也不会卡住。探测失败只降低 ApiKind 的置信度并写入 notes，不会让整个探测失败。

能力位是前端唯一的驱动差异来源

前端不判断「这是哪个驱动」，只读 GET /api/instances/:id 返回的 capabilities。不支持的操作在界面上灰化，并展示具体原因。

配置写入流程

本机与远程走同一套语义：

1. 校验（schema / 目标二进制）      失败 → 不写
2. 读取旧文件 → 备份到 <file>.bak.<UTC 时间戳>
3. 写临时文件 <file>.tmp.<rand>（权限递归自旧文件）
4. fsync → rename 覆盖（POSIX 原子；Windows 用替换语义）
5. 校验目标文件内容哈希一致
6. 触发 reload；失败且策略为 auto_restart → 重启
7. 记审计（备份路径、文件 sha256 前后值，不含密钥内容）
配置编辑会丢失注释

保存时按 TOML 值序列化，注释不保留。请以备份回滚兜底；需要保留注释的场景请直接改文件后再让面板读取。

代理：先分清来源

ProxyInfo 用 source 与 managed_by 区分「配置文件里定义的」「面板动态加的」「服务端推送的」。删除时按来源选择端点：客户端本地动态代理走客户端 Admin API；服务端推送的代理走服务端 Admin API（带 run_id 与名称）。NFrp 0.5.5 起，远程下发不能删除或覆盖配置文件里定义的代理。

监控与日志

指标能力分三档：full（NFrp，含流量字节）、aggregated（官方 frps，仅连接数与在线态）、none。日志来源分 file / remote / journal，在同一个 LogPage 结构里返回，前端不需要按驱动分支。

SSH 部署

SshBinaryDriver 负责远程预检、上传、安装、启动与回滚。每一步都能在部署页签看到状态、日志与失败原因。

前置条件

项要求检查方式
目标系统Linux（systemd 或 nohup）预检第 1 项
SSH 服务端口可达，允许密码或公钥登录向导「测试连接」
sudo免密（sudo -n）或 root预检「sudo 权限」
本机 sftp面板所在主机有 sftp 命令预检「上传二进制」
磁盘≥ 200 MB预检「磁盘空间」
sudo 需要密码时面板会明确失败

面板不做交互式提权。请给对应用户 NOPASSWD，或改用 root 登录，或选择 sudo -n 模式。

首次连接与主机指纹

面板默认拒绝未知主机，没有「跳过校验」的开关。流程是：

  1. 点击「测试连接」；
  2. 若主机未受信任，后端只完成 SSH 握手、不发送任何凭据，返回指纹（SHA256:…）；
  3. 前端展示指纹，要求人工比对；
  4. 确认后写入 host_keys 表，并同步到面板的 known_hosts 供 sftp 子进程二次校验；
  5. 指纹与已保存记录不一致时拒绝连接——要用新指纹必须先移除旧记录。

在目标机上核对：

ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
# 输出形如：256 SHA256:xxxxxxxx... root@host (ED25519)

面板的指纹算法是 SHA256:base64，与 ssh-keygen -lf 一致（去掉末尾 =）。

环境探测

全部使用只读命令，结果决定后续默认值：有 systemd 就用 systemd，没有则自动切到 nohup 并在界面标注。

探测项命令（白名单生成）
OS / 内核 / 架构 / 主机名uname -s; uname -r; uname -m; hostname
systemdcommand -v systemctl && echo yes || echo no
用户与 sudoid -un; sudo -n true && echo sudo:nopasswd || echo sudo:password
磁盘可用df -Pm <dir> | awk 'NR==2{print $4}'
已装 frp遍历 /usr/local/bin/{frps,frpc}、/usr/bin/{frps,frpc}
端口占用ss -Hltn 或 netstat -ltn

安装来源

  • 使用远端已有 — 只下发配置，不替换二进制，适合接管已有安装
  • 上传本地文件 — 浏览器读取 → base64 → 后端解码 → SFTP 上传
  • 从 URL 下载 — 后端下载（限 128 MB），可带 SHA256 校验

三种来源最终都先落到 /tmp/frppanel-<name>-<时间戳>。校验规则：SHA256 必须一致（上传后远端再算一次 sha256sum）；读 ELF 头的 e_machine 判断架构（amd64 / arm64 / arm / 386），与目标机 uname -m 不一致直接失败；PE 文件（Windows）会被明确拒绝。

部署执行顺序

[probe]           探测环境（只读）
[upload_binary]   SFTP 上传到 /tmp
[verify_binary]   远端 sha256sum + ELF 架构校验
[install_binary]  备份旧二进制 → mv 原子替换 → chmod 0755
[write_config]    备份旧配置 → 写临时文件 → mv 原子替换
[write_unit]      写 /etc/systemd/system/<unit>.service（无 systemd 跳过）
[daemon_reload]   systemctl daemon-reload
[enable_service]  systemctl enable
[write_pid_dir]   nohup 模式：准备日志目录
[start_service]   systemctl restart 或 nohup 启动
[wait_admin_api]  轮询 /api/healthz → /api/v2/status → /api/status（最多 25 秒）
[verify_status]   读取二进制版本，落库部署状态

重复部署会先备份 <binary>.bak.<时间戳> 与 <config>.bak.<时间戳> 再覆盖；配置文件用「临时文件 + mv」替换，不会出现半个文件。

失败回滚

  • 启动命令非零退出；
  • 25 秒内 Admin API 未就绪。

出现上述情况时，面板把备份的二进制与配置复制回去，把任务标为 rolled_back，并在失败步骤上显示修复建议。回滚只还原二进制与配置，不尝试重启服务，避免掩盖问题。

手动回滚入口：详情页「部署」页签的回滚按钮；配置页签「历史备份」→ 选择某份 →「恢复」。

systemd unit 模板

[Unit]
Description=frp server (managed by FrpPanel)
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
ExecStart=/usr/local/bin/frps -c /etc/nfrp/frps.toml
WorkingDirectory=/var/lib/nfrp
Restart=on-failure
RestartSec=5s
LimitNOFILE=65535
StandardOutput=journal
StandardError=journal
SyslogIdentifier=nfrp-server
NoNewPrivileges=true
ProtectSystem=full
ProtectHome=true
PrivateTmp=true

[Install]
WantedBy=multi-user.target

查看日志：journalctl -u nfrp-server -f。无 systemd 时同一模块生成 nohup 守护脚本（start / stop / restart / status），用 <config>.pid 记录 PID；该模式不会开机自启，界面会标注「非 systemd 模式」。

Admin API 必须能从面板主机直连

若 frp 面板端口只监听 127.0.0.1，wait_admin_api 会失败并回滚。请把 webServer.addr 改为 0.0.0.0（务必配强口令），或自建隧道。

已知限制

  • SFTP 依赖系统 OpenSSH 客户端（russh 0.54 不含 SFTP 实现）；主机密钥仍由 russh 校验，sftp 另带 StrictHostKeyChecking=yes
  • sudo 需要密码的场景不支持；ssh-agent 认证未实现
  • 尚未在大量 Linux 发行版上做矩阵验证，代码路径与预检逻辑完备，欢迎按上面的清单在你的环境验证

驱动与能力探测

同一套语义，四种实现；调用方不需要判断驱动类型。无法提供的可选能力用「能力位 + 明确的错误」表达，而不是撒谎返回空数据。

四种驱动

驱动接管进程拥有配置能做什么不能做什么
BinaryDriver（默认）✅ 本机✅启停、读写配置、reload、代理管理、指标—
SshBinaryDriver✅ 远程✅同上 + 远程部署 / 预检 / 回滚需要 SSH 凭据与 sudo
AdminApiDriver❌❌状态、代理（仅 NFrp）、指标启停、编辑配置、日志
EmbeddedDriver——预留接口第一版未实现，调用返回明确错误

怎么选：默认用 BinaryDriver；要管远程服务器用 SshBinaryDriver；只想把一个已经在跑的实例纳管起来看一眼（不改配置、不重启），用 AdminApiDriver。

能力位

能力探测的结果是一个 Capabilities 对象，随实例详情返回并落库。前端只读这份数据来决定按钮是否可用。

pub struct Capabilities {
    pub flavor: BinaryFlavor,            // Nfrp | OfficialFrp
    pub flavor_version: Option<String>,
    pub api_kind: ApiKind,               // Nfrp | Official | Unknown
    pub managed_locally: bool,
    pub remote: bool,
    pub can_start_stop: bool,
    pub can_reload: bool,
    pub can_edit_config: bool,
    pub can_dynamic_proxy: bool,
    pub can_manage_visitors: bool,
    pub has_v2_api: bool,
    pub has_healthz: bool,
    pub prometheus: PrometheusSupport,   // Off | Enabled | Unknown
    pub metrics_detail: MetricDetail,    // Full | Aggregated | None
    pub auth_guard_header: bool,         // NFrp 客户端写操作需 X-Nfrp-Client

}

探测算法

  1. 取 Admin API base 与凭据。凭据从面板加密存储中解密，仅在服务端内存中出现。
  2. 并发请求 GET /api/v2/version、/api/v2/status、/api/status、/api/healthz。
  3. 按命中组合判定 ApiKind：v2/version 命中且含 frp_wire_version ⇒ 极可能是 NFrp；/api/status 顶层有 clients[] ⇒ NFrp 服务端；顶层有 tcp[]/udp[]/http[] 键 ⇒ 官方 frpc；/api/v2/* 返回 {code,msg,data:{items,total}} 信封 ⇒ 官方服务端。
  4. 版本优先取 /api/v2/version.data.server，否则取二进制 -v（本机 / SSH），最后取 clients.version。
  5. 把结果连同证据（哪个端点返回什么状态码）落库，前端「能力」页签原样展示。

判定必须容错且可解释：任何一项拿不到都不应让整体探测失败，只降低 ApiKind 置信度并写入 notes。

reload 的三种结果

这是本项目的核心正确性点。服务端没有 reload 端点，热重载靠轮询配置文件 mtime。

pub enum ReloadOutcome {
    Hot,                                  // 已热生效
    RestartRequired { fields: Vec<String> }, // 该字段无法热改
    Unsupported,                          // 当前实现不支持
}
BinaryDriver/NFrp     → 写文件 → 轮询 mtime（≤3s）→ 抓 /api/v2/status 比对
                      → 成功 Hot；字段无法热改 → RestartRequired
BinaryDriver/Official → 写文件 → 若进程以 --enableReload 运行 → 触发 reload
                      → 否则 RestartRequired（可选 auto_restart_on_save）
Client 侧（两边）      → 重写 [[proxies]] 后重启或触发热加载
AdminApiDriver        → Unsupported（只有所有者能改配置）

AdminApiDriver 的边界

它没有配置文件所有权，因此不能编辑配置、不能改变代理的持久定义。对 PUT /api/instances/:id/config 与持久化语义的 PATCH .../proxies/:name 返回 409 driver_immutable；对启停返回 409 driver_unsupported。前端灰化按钮并给出原因，而不是假装成功。

实例列表里的能力

能力探测在启动 / 连接时执行，结果缓存并落库。实例列表先读本地记录秒开，后台再逐个探测；探测结果会更新版本、能力位与连接状态，但不改变列表的可用性。

HTTP API

前端只与本后端通信，永不直连 frp Admin API。以下为契约摘要，完整字段见仓库中的 docs/02-api.md。

基础约定

  • Base：/api
  • 认证：Authorization: Bearer <access_token>（登录与健康检查除外）
  • 内容：application/json; charset=utf-8
  • 时间：RFC3339 UTC，例如 2026-11-03T13:47:04Z
  • 分页：?page=1&page_size=20 → { items, pagination: { page, page_size, total, total_pages } }
  • 流：SSE（text/event-stream），事件 step / log / done / error，带 id 便于断线续传

架构

后端 Rust（Axum 0.8 + tokio + sqlx/SQLite），前端 Vue 3 + TypeScript。分层的目的只有一个：驱动差异不扩散。

分层图

Vue 3 + TS（自绘组件 + ECharts）
   │  /api/*（JWT；只与本后端通信，永不直连 frp Admin API）
   ▼
Axum API 层（api/）── RBAC ── 审计
   │
   ▼
Driver trait（driver/）
 ├─ BinaryDriver    本机进程 + 配置文件 + Admin API
 ├─ SshBinaryDriver SSH 部署 + systemd/nohup + 远程配置
 ├─ AdminApiDriver  仅 Admin API（不接管进程、不拥有配置）
 └─ EmbeddedDriver  预留：进程内链接 nfrp-common
   │
   ├── frpapi/      NFrp / 官方 frp 双实现适配 + 能力探测
   ├── configfile/  校验（复用 nfrp-common）+ 备份 + 原子写
   ├── ssh/         russh 会话 + 主机指纹 + 白名单命令 + sftp
   ├── deploy/      预检 → 分步执行 → SSE 流 → 失败回滚
   ├── metrics/     采样落库 + 趋势查询
   └── db/          SQLite（实例、凭据密文、审计、备份、任务）

分层约束

  • api/ 只做「参数 → 领域调用 → DTO」，不直接发 frp 请求
  • driver/ 只回答「这个实例能做什么」，能力位是前端唯一的驱动差异来源
  • frpapi/ 是兼容性的唯一出口，NFrp / 官方差异只在这里出现
  • db/ 不出现任何驱动细节

NFrp 客户端 API

端点鉴权结果
GET /api/statusBasic200 {data:{client_id, connected, run_id, proxies:[...]}}
GET /api/proxiesBasic200 {data:[{name,type,local_addr,remote_port,...}]}

重要语义差异：通过服务端推送的代理不在客户端本地表里，客户端 POST /api/proxies/remove 会失败。删除必须按来源选择端点：客户端本地动态代理走客户端 Admin API；服务端推送的代理走服务端 Admin API（带 run_id 与名称）。

NFrp 热重载

  • 服务端每秒轮询配置文件 mtime，变化后重新解析并应用可热改字段；解析失败忽略本次变更；安全闸门不通过则拒绝
  • 实测改写 log_level 后 4 秒内日志出现热重载记录，进程未重启
  • 没有 HTTP reload 端点，未处理 SIGHUP
  • Windows 上 taskkill /PID 优雅终止，实测 103 ms 内退出

因此面板的 reload() 是「写文件 + 等生效 + 校验」，不是「调一个 API 就完事」。

官方 frpc 配置严格性

把 webServer.* 写在 [[proxies]] 之后时，官方 frpc 直接退出：

decode proxy at index 0: unmarshal ProxyConfig error: json: unknown field "webServer"

因此面板下发配置必须：使用目标二进制认识的字段名；生成时把全局段放在所有 [[proxies]] 之前；用目标二进制的 verify / --check 做最后一道校验。

对实现的直接影响

  • reload 语义按 flavor 分流，禁止假设存在 reload 端点
  • Admin API 适配层区分 nfrp / official 两套结构，ApiKind 存库
  • 写操作自动附加 X-Nfrp-Client: 1（仅 NFrp 客户端）
  • 代理删除按来源选择端点（客户端本地 / 服务端推送）
  • 官方 frpc 的代理增删走配置文件 + 重启
  • 配置生成按目标 flavor 输出字段，官方目标剔除 NFrp 专有段
  • 指标能力位区分 Full（NFrp 字节）/ Aggregated（官方连接数）/ None
  • Windows 停止进程使用优雅终止并等待，再强制

安全说明

面板不内嵌 Go 运行时，也不做黑盒中间层；安全边界写在代码里，而不是文档里。

凭据加密

  • SSH 密码 / 私钥、Admin API 密码使用 AES-256-GCM 加密存储，每次加密随机 96-bit nonce，AAD 绑定 credential:<id>:secret
  • 主密钥来自 data/master.key（权限 0600）或环境变量
  • 前端永不回显明文，列表只显示「是否已设置」；接口返回 has_secret 与 ••••••••
  • frp 管理密钥不出后端：浏览器只拿到 admin_api: { base_url, user, password_set: true }
  • JWT 仅存 sessionStorage，不落 localStorage；前端无任何 frp Admin API 直连
master.key 不能丢也不能泄露

丢失后已存凭据无法解密，需要重新录入。备份时把 master.key 与数据库分开保管。

SSH 安全

  • 主机指纹首次确认、变更拒绝；没有「关闭主机密钥校验」的开关
  • 只执行白名单模板命令（systemctl、install、chmod、mkdir、sha256sum、mv、tar 等），参数严格转义
  • 路径参数再过字符白名单，拒绝 ; | & $ ` < > ( ) { } * ? ! " '
  • 自定义提权命令默认关闭（allow_custom_command = false），且禁止管道 / 重定向 / 命令替换
  • 凭据不落盘：SSH_ASKPASS 临时脚本权限 0600，用后即删；sftp 另带 StrictHostKeyChecking=yes
  • 审计记录主机、操作、结果与耗时，不含凭据内容

RBAC

只有两级：admin 可写，viewer 只读。写接口在提取器层拒绝，不依赖每个 handler 自觉判断。SSH 凭据与部署操作仅 admin 可用。面板暂无用户管理界面，创建 viewer 需直接写库。

审计

  • 记录登录、实例变更、配置写入、启停、代理增删、凭据增删、部署与回滚
  • secret 类型字段在写入前统一走 secret::redact；日志走 redact_line 脱敏
  • 按 retention_days 由数据库保留策略自动清理，没有清空接口

部署安全清单

  1. 面板默认只监听回环地址。要暴露到公网请用 Nginx / Caddy 反向代理 + HTTPS，并保持 bind = 127.0.0.1:8787
  2. 首次登录后立刻改密码，并删除 data/admin.initial
  3. 两个密钥文件不能丢也不能泄露：data/master.key 与 data/jwt.key
  4. frp 自身的安全配置面板不代劳：token 强度、transport.tls.force、面板端口凭据仍需在 frp 配置里设好；配置诊断会给出提醒
  5. RBAC 只有两级（admin / viewer）。viewer 只读，写接口在提取器层拒绝

面板不代劳的 frp 配置

面板管理的是「进程、配置、部署、观测」，不是 frp 的安全策略本身。请在实例配置中自行确认：

  • auth.token 使用足够长的随机口令
  • 对外暴露时开启 transport.tls.force
  • Admin API 面板端口设置强口令，避免只监听 127.0.0.1 导致远程部署时不可达
  • 不要把 NFrp 专有段（[nlink]、[vnet]）下发给官方 frp（会直接退出）

常见问题

先看这里，再看对应的功能页。

FrpPanel 与 NFrp 是什么关系？

FrpPanel 是管理面板，NFrp（Rust-Frp）是它管理的 frp 实现之一。面板通过 path 依赖复用 nfrp-common 做配置解析与校验，这是「与 NFrp 同源」的具体体现，不是中间层。面板也管理官方 frp 的 frps / frpc。

能管官方 frp 吗？

能。驱动、能力探测与 DTO 都覆盖官方 frp；差异体现在能力位：官方 frps 没有 /api/status、/api/healthz，没有热重载，也没有流量字节。界面会灰化不支持的操作并说明原因。

为什么官方 frp 的代理不能动态增删？

官方 frpc 0.71.1 的 PUT /api/config 实测返回 200 但代理并未生效，PUT /api/config/{name} 返回 404。这是官方 API 的现状，不是面板的取舍。面板对官方 frpc 采用「配置文件改写 + 重启」。

为什么改完配置要重启？

官方 frps 没有热重载端点，NFrp 服务端也只靠每秒轮询配置文件的 mtime。面板会返回 hot / restart_required / unsupported，必要时按 auto_restart_on_save 自动优雅重启。

为什么官方 frps 没有流量字节？

官方 frps 的 /api/v2/proxies 只提供连接数与今日流量字段，面板将其能力位标为 aggregated；NFrp 才提供完整的字节计数（full）。

SSH 部署失败了怎么排查？

先看部署任务对应的失败步骤与 remediation。常见原因：sudo 需要密码、目标端口被占用、Admin API 不可从面板主机直连、上传的二进制架构不匹配、25 秒内服务未就绪。也可以按SSH 部署页末尾的手工验证清单逐项核对。

sudo 有密码行不行？

不行。面板不做交互式提权，请配置 NOPASSWD，或使用 root 登录，或选择 sudo -n 模式。

忘记管理员密码？

echo 你的新密码 | cargo run -p frp-panel -- --reset-admin-password --admin-username admin

新密码从 stdin 读取，不会出现在进程列表里；成功后旧的 data/admin.initial 会被删除。此入口只适合本机管理员使用。

master.key 丢了怎么办？

已存凭据无法解密，需要重新录入 SSH / Admin API 凭据。数据库本身以及实例、审计记录不受影响。

怎么创建 viewer 用户？

目前没有用户管理界面，只有「至少一个管理员」的初始化。创建 viewer 需要直接向 users 表写入记录（角色 viewer）。

审计日志能删吗？

不能。审计日志只按 retention_days 由数据库保留策略自动清理，没有清空接口。

支持 Windows 吗？

面板后端可在 Windows / Linux 运行，本机二进制驱动在 Windows 上可用。SSH 远程部署的目标机要求 Linux，并具备 systemd 或 nohup。

已知限制

  1. EmbeddedDriver 未实现 — 预留 trait 与错误路径，调用返回明确提示
  2. 官方 frp 的代理动态增删不可用 — 面板改写配置文件后重启；0.71.1 实测 PUT /api/config 返回 200 但不生效
  3. 官方 frps 没有热重载 — 保存配置后需重启；可开启「保存后自动重启」
  4. 官方 frps 不暴露流量字节 — 监控只画连接数 / 在线态，能力位标为 aggregated
  5. SSH 的 SFTP 依赖系统 OpenSSH — russh 0.54 不含 SFTP 实现，面板用 sftp 子进程传输；主机密钥仍由 russh 校验
  6. SSH 模式尚未在大量 Linux 发行版上做矩阵验证 — 代码路径、单元测试与预检逻辑完备，开发环境覆盖有限
  7. ssh-agent 认证未实现 — 返回明确错误并建议改用密码 / 私钥
  8. 没有用户管理界面 — 创建 viewer 需直接插入 users 表
  9. 审计日志不可删除 — 只按保留天数自动清理
  10. 远程 Admin API 需要可从面板主机直连 — 若 frp 面板端口只监听 127.0.0.1，预检会明确指出
  11. 配置编辑会丢失注释 — 保存时按 TOML 值序列化
